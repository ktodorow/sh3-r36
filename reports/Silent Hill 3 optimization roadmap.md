## Current frame costs require CPU and graphics improvements

Both final profiles use the same checkpoint, fixed camera, 55–95-second warm analysis window, no screenshots, 640×480 output, and the same controlled graphics values. These are instrumented static-scene results, not full-route acceptance. ([640 summary](../r36s-dumps/sh3/20261113T174837069025Z-36b849/frame-summary.json), [320 summary](../r36s-dumps/sh3/20261113T175211968006Z-bdd0f6/frame-summary.json))

| Measurement | 640×480 internal | 320×240 internal |
| --- | ---: | ---: |
| Mean-derived FPS | **13.5846** | **17.0724** |
| Mean frame time | 73.613 ms | 58.574 ms |
| Frame p50 / p95 / p99 / max | 73.150 / 78.396 / 80.426 / 84.684 ms | 58.434 / 60.546 / 63.305 / 121.493 ms |
| Presenting-thread CPU p50 | 42.392 ms | 42.849 ms |

Budget reductions are arithmetic sizing, **not predicted gains**. CPU includes game, renderer, driver and diagnostics; draw elapsed includes host work and waits; swap is inside Present. Their medians overlap and cannot be added into a frame budget. Swap duration is not GPU execution time. Lower resolution cuts presentation elapsed substantially while current CPU/draw costs remain similar, so resolution alone has not solved this build's bottleneck. ([counter boundaries](../src/d3d8/profile.c), [Present](../src/d3d8/d3d8.c))

Existing fixes show useful progress: sampler parameters fell from 3,648 to 138 calls and attribute enable/disable operations from 1,393 to 18 across 76 diagnostic draws. Against the corrected 640 baseline, both caches improved FPS approximately **15.9%**, draw elapsed 37.0%, and presenting-thread CPU 18.4%. Earlier 9.48/11.73-FPS baselines included expensive automated-input parsing; that diagnostic overhead must not be credited as a physical-play renderer gain. No corrected pre-cache 320 baseline exists. ([experiment record](issue-13-performance.md))

Warm 640 sampling records 1,419 native-code and 757 Mali-library observations among 2,312 total. Mali samples measure driver **CPU execution**, not GPU occupancy; native samples include renderer/runtime as well as guest logic. The 42–43-ms CPU measurement is therefore a target for improvement, not a permanent hardware floor. Elapsed-step repair currently allows roughly four guest ticks per slow 320 frame and six at 640, compared with two at 30 FPS. If some work scales with elapsed ticks, faster rendering can also reduce catch-up work per frame; measure calls/work per guest tick before assigning that effect a gain. Never shrink simulation steps to manufacture FPS. ([symbolized samples](../r36s-dumps/sh3/20261113T174837069025Z-36b849/cpu-symbols.json), [timing evidence](issue-09-audio-timing.md))

The quoted 512-MB PC RAM requirement cannot establish this port's frame rate. Current controlled runs show no RAM exhaustion or recorded clock reduction: CPU/GPU/DMC remain 1512/520/786 MHz. Native translation, driver submission, bandwidth and pacing determine per-frame cost even when assets fit memory. Full-campaign memory and hot-session behavior still require evidence. ([telemetry](issue-13-performance.md), [memory/runtime analysis](Silent%20Hill%203%20R36S%20feasibility.md))

## SH2 supplies concrete renderer changes to adapt

**The strongest new source lead is SH2's existing cache implementation.** Reviewed SH2 v1.03 is pinned to `7e69609f3a063fbe24c41d6aa560f14ede578746`; cache introduction is `9edc6c39a318a0b4bc0b6542893b4b7aae521290`. This port's SH3 upstream remains `ff483a6f95b94a4f7924f6fbe4cb47169f2adb98`. Shared lineage supplies implementation examples for per-program uniforms, matrices, central GL state/bindings, and attachments. It supplies no transferable FPS guarantee. ([SH2 cache change](https://github.com/cutarev/sh2-nx/commit/9edc6c39a318a0b4bc0b6542893b4b7aae521290), [pinned SH3](https://github.com/cutarev/sh3-nx/tree/ff483a6f95b94a4f7924f6fbe4cb47169f2adb98))

Current SH3 calls `glUseProgram` every draw, repeatedly uploads shader constants and fixed-function values, looks up three lighting uniform names, and rebuilds matrices even when inputs or active uniforms do not require it. State setup repeatedly emits viewport, depth/blend/cull/stencil/mask operations; texture setup visits eight stages. Start with the following independent slices, counting avoided work and checking unchanged pixels. ([current binder](../src/d3d8/d3d8_shader.c), [draw/state setup](../src/d3d8/d3d8.c))

| Local slice | Concrete change | Keep gate and failure cases |
| --- | --- | --- |
| Uniform locations | Resolve `uPower`, `uLtSpecular`, `uLtAmbient` once when linking. | Eliminate repeated lookups; unchanged pixels. Small first patch, not a claimed 30-FPS fix. |
| Effective uniform values | Store fresh flag and last uploaded payload **per linked program**; start with scalars, then constants/materials/lights. Upload first use and changed bytes. | Demonstrate real reuse and lower CPU/frame. Program A→B→A, warm startup, menus, doors and reset must retain correct values. |
| Matrix reuse | Rebuild products/inverses only when effective inputs change and active shader needs them. | Fewer rebuilds and repeatable end-to-end gain; same transforms, lighting and animation. |
| Program/state/bindings | Adapt central ownership gradually: program, enable/write/viewport state, textures and buffers. | Fewer API calls without stale state after Clear, Present, upload, copy/readback, creation or deletion. |
| Attachment reuse | Compare actual color/depth object, storage epoch, face and mip; retain viewport-reset semantics and spare-depth handling. | Fewer attachments/status checks; correct target switches, fades, resolution changes and save images. |

SH2 demonstrates [per-program retained values/generations](https://github.com/cutarev/sh2-nx/blob/7e69609f3a063fbe24c41d6aa560f14ede578746/src/d3d8/d3d8_shader.c#L732), [central state ownership](https://github.com/cutarev/sh2-nx/blob/7e69609f3a063fbe24c41d6aa560f14ede578746/src/d3d8/d3d8.c#L12), and [attachment reuse](https://github.com/cutarev/sh2-nx/blob/7e69609f3a063fbe24c41d6aa560f14ede578746/src/d3d8/d3d8_res.c#L320). Adapt these narrowly. Its desktop clip/depth behavior and opaque P8 upload would regress SH3's GLES orientation/depth, palette alpha/versioning and resource fixes. Its streaming-ring change also needs separate lifetime testing. ([SH2 resource differences](https://github.com/cutarev/sh2-nx/blob/7e69609f3a063fbe24c41d6aa560f14ede578746/src/d3d8/d3d8_res.c#L284), [current SH3 resources](../src/d3d8/d3d8_res.c))

Cache correctness is the main engineering constraint. Compare **effective** constants after declaration `v->const_set` overlays, not device constants alone. Prefer payload comparison first; generation counters become safe only after auditing setters, state-block restoration, defaults/reset and direct copies. Program creation/warmup must use the same binder. Clear/Present, uploads, spare-depth creation, readback and copies mutate actual GL state and must update or invalidate shared caches. Texture keys include unit/target and deletion/name reuse; element-buffer/attribute state belongs to its VAO. A cache that remembers requested D3D state while helper GL calls change actual state will silently corrupt scenes. ([SH3 shader merge and writers](../src/d3d8/d3d8_shader.c), [device/resource mutations](../src/d3d8/d3d8.c), [cache ownership research](../research_notes/Silent%20Hill%203%20optimization%20roadmap/gpu_renderer.md))

After call reduction, the clearest bandwidth candidate is Present's **second full-frame blit** into `res_snapshot_front()`. Retaining/ping-ponging backing textures could preserve the last presented image without copying every frame; output still needs its scale/flip blit. Deleting the snapshot is invalid because transitions and `GetFrontBuffer`/save images consume it. Build an independent last-presented-image oracle covering clear-after-present, aliases, locks, copies, resource lifetime and resolution changes before changing ownership. Arm's tile-renderer guidance supports reducing unnecessary framebuffer traffic and preserving pass locality, but never discarding contents a later guest pass reads. ([current snapshot/copy path](../src/d3d8/d3d8_res.c), [Arm framebuffer guidance](https://developer.arm.com/community/arm-community-blogs/b/mobile-graphics-and-gaming-blog/posts/mali-performance-2-how-to-correctly-handle-framebuffers))

Texture work needs one missing evidence slice before optimization: allocated/uploaded bytes by format/mip, decode and palette-expansion counts, dirty reasons, lock flags, readback bytes/time, and render-target switches/dimensions. Existing 140-KB counters cover **vertex/index bytes only**. Warm `decode_blocks` samples justify checking repeated unchanged uploads, read-only unlocks and resource churn; they do not establish the cause. If duplicates are proven, fix dirty semantics first, then reuse conversion scratch or bound an exact decoded cache. Preserve DXT1 transparency, DXT2/4 premultiplied bytes, mips and animated P8 alpha. ([resource implementation](../src/d3d8/d3d8_res.c), [warm evidence](issue-13-performance.md))

Later GPU experiments should follow the residual bottleneck: right-size demonstrated oversized render targets; retain immutable texture storage and upload at safe loading boundaries; inspect hot shaders before reducing proven-bounded precision; batch only compatible adjacent draws without changing transparency/stencil order. Keep depth/position precision and required RHW `gl_FragDepth` recovery unless an independent depth oracle proves a narrower variant safe. Current PortMaster FNA guidance supplies comparable cases involving oversized targets and redundant copies, but FNA/Mono differs from this D3D8 bridge. ([PortMaster FNA guide](https://portmaster.games/contribute/porting/engines/fna/), [Mali-G31 optimization guide](https://documentation-service.arm.com/static/64d496a94a92140bb31d7b96?token=), [shader generator](../src/d3d8/d3d8_shader.c))

Actual native GLES advertises ASTC but lacks tested native S3TC, so current DXT fallback expands to RGBA8. ASTC advertisement does not prove texture operations or authorize lossy asset conversion. GPU texture conversion is credible only for sufficiently large retained GPU-only work with exact filtering/alpha/mip behavior. Translated vertex/fixed-function shader work already runs on GPU; moving synchronous AI, collision or individual guest matrices there adds synchronization and readbacks unless consumers stay GPU-resident. The GPU can help by receiving less redundant submission and memory work first. ([native operation log](../r36s-dumps/sh3/20261113T175641744991Z-7b8214/device/execution.stdout.txt), [GPU experiment boundaries](../research_notes/Silent%20Hill%203%20optimization%20roadmap/gpu_renderer.md))

## Exact native kernels target remaining CPU cost

`recomp_fp_round24` is the largest named native leaf, 219/2,312 samples, approximately **9.5%**; signed-byte filter `sub_004464E0` has 69 and matrix multiply `sub_00648639` 59. These are leaf observations, not inclusive costs. Matrix callers also spend time inside rounding helpers, so do not assign independent additive gains to those bins. Reprofile after renderer work to select the remaining kernel by total cost. ([sample mapping](../r36s-dumps/sh3/20261113T174837069025Z-36b849/cpu-symbols.json))

**Replacing rounding with a float cast is not a new optimization.** Current normal-range path already uses hardware `FCVT` double→float→double; exceptional finite magnitudes retain a larger exponent range through `frexp`/`ldexp`. A plain cast-only replacement breaks that behavior. A shorter bitwise range guard or bounded inlining experiment remains testable, but needs independent ties, signed zero, NaN/infinity, exponent-boundary and control-mode cases, then real CPU/frame improvement. ([pinned helper](https://github.com/cutarev/sh3-nx/blob/ff483a6f95b94a4f7924f6fbe4cb47169f2adb98/third_party/xboxrecomp/templates/runtime/recomp_types.h#L273), [exact-artifact disassembly findings](../research_notes/Silent%20Hill%203%20optimization%20roadmap/cpu_runtime.md))

The stronger structural candidate is a scalar-native override for matrix function `0x00648639`, removing emulated register, TLS FPU-stack and guest-stack traffic while preserving arithmetic order and rounding after every operation. Start scalar; then parallelize independent outputs with AArch64 NEON, retaining per-lane order and exceptional/control-mode fallback. Do not use FMA or reassociate sums. The signed-byte filter offers a separate scalar/NEON candidate after caller/data ownership is known; preserve signed widening, arithmetic shifts, wrap, boundaries, aliases, scratch and observable guest state. Arm intrinsics establish supported operations, not application speed. ([matrix](../src/recomp/gen/recomp_0040.c), [filter](../src/recomp/gen/recomp_0006.c), [Arm NEON intrinsics](https://arm-software.github.io/acle/neon_intrinsics/advsimd.html))

Before arithmetic rewrites, strengthen the oracle: current snapshots retain x87 top/stack data, but replay does not restore that stack/control state, control word is absent, and mismatch reporting lacks a reliable failure exit. Expected rounding expressions partly duplicate the implementation. Capture/restore relevant integer/FPU state and full writes; prove deliberate corruption fails; compare against original x86 execution or an independently specified bit-level rounding reference. Cover output aliasing either matrix, unusual overlap, cancellation, signed extremes and unsupported-mode fallbacks. Then require unchanged real-game geometry, movement, collisions and combat. ([oracle](../tools/oracle.py), [snapshot writer](../src/runtime/rt_core.c), [precision tests](../third_party/xboxrecomp/tests/fp_precision/fp_precision_test.c))

The build already uses GCC 12.2, `-mcpu=cortex-a35 -O2 -fwrapv -fno-strict-aliasing`; debug symbols do not imply an unoptimized binary. Compare O3 alone, O2+LTO, then combined only if justified, retaining ABI and semantic flags and recording code size, build resources and symbolization. Reject incorrect or slower variants; avoid fast-math and unchecked contraction. Flat dispatch is already present, and three lookup leaves together account for only approximately 3% of samples: dispatch/trace tuning is lower priority unless new inclusive evidence changes that ranking. No overclock or firmware/global-library change is required for these experiments. ([compile commands](../.port-cache/builds/20261113T174635538228Z/compile_commands.json), [GCC optimization semantics](https://gcc.gnu.org/onlinedocs/gcc-12.2.0/gcc/Optimize-Options.html), [runtime dispatch](../src/runtime/rt_core.c))

## Conclusion

The next engineering decision is concrete: begin the narrow uniform-cache series and establish a clean comparison alongside it. Shared SH2 source exposes removable submission work; the snapshot path exposes avoidable-copy architecture; exact native kernels provide a CPU route if that remains limiting. Their combined value must emerge from matched measurements, without adding overlapping estimates or promising unsupported gains.

**30 FPS remains the completion target and is currently unpassed.** Work should advance one retained improvement at a time toward a reproducible heavy-route candidate, then verify that artifact at original speed on the handheld. Keep all changes local while this work continues; the user's canceled publication instruction remains in force.
