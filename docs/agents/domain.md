# Domain context

Read before exploring domain terms or changing glossary/ADRs.

1. Read root [GLOSSARY.md](../../GLOSSARY.md), relevant records in [docs/adr/](../adr/), and canonical feature spec linked by selected task. If no spec exists, use README and project research while drafting one.
2. Use **Full port**, **Internal resolution**, **Output resolution**, **Game data**, and **PortMaster package** as defined in glossary. Proof-of-life milestones do not satisfy Full port acceptance.
3. For port/runtime decisions, read full [feasibility report](../../reports/Silent%20Hill%203%20R36S%20feasibility.md) and [working-port notes](../../research_notes/Silent%20Hill%203%20R36S%20feasibility/working_port_patterns.md), including their referenced evidence where relevant.
4. Keep user-confirmed requirements, source observations, historical device results, proposed work, and current verified capabilities distinct. Another port's success establishes a reference pattern, not SH3 acceptance.

When terminology or architectural decisions change, use domain-modeling skill. Glossary stores meanings without implementation details; canonical spec stores feature acceptance; ADRs explain substantial accepted trade-offs. Keep private connection settings and user-specific reference paths in ignored local configuration.
